2) BREL 程式需要怎麼改？（最小修改集 + 不破壞你既有「One Spine」）
我用「BREL very lite → BREL full」都能吃的方式講：你不用重寫，只要在 BREL 的四個位置加“隱私鉤子（privacy hooks）”。
改動點總覽（四個地方）
Proof Card 生成（輸出面）：把 Proof Card 變成 PC-Min / PC-Priv 雙層
Admission/Gate 判定（門控面）：隱私成為有效性前提（privacy as validity precondition）
Egress/Export（外送面）：加一個 Minimal-Disclosure Egress Gate（最小揭露出口閘）
BYUSE / 升級（效果面）：一旦被用於客服結案/監管/賠付，觸發 requiredness（不給就 not-closure-grade）
A) Proof Card：新增 PC-Min / PC-Priv（不動你現有欄位，只做分層）
你現在的 Proof Card 欄位（attempt_id/verdict/window_ref/reason_code/version refs…）都保留。
新增做法：同一個 attempt_id 產生兩張卡（或一張卡兩個 section）：
PC-Min（跨供應商、跨域通用，預設可外送）
只保留必要可驗欄位，例如：
attempt_id
enforcement_path_id / gate_ref
verdict（READY/NOT_READY/INSUFFICIENT…）
window_ref（或 episode_ref）
basis/version refs（policy_snapshot_ref、window_policy_id、translation_basis_id 如需）
missing_evidence_class（若不夠）
upgrade_requirements_ref（若 BYUSE 觸發要補件）
PC-Priv（內部/受控，預設不可外送）
新增 refs（不放 payload）：
privacy_policy_ref（或 privacy_constraint_set_ref）
purpose_ref（用途類別）
retention_ref（保存策略類別）
disclosure_scope_ref（可揭露範圍/粒度/欄位集合）
redaction_profile_ref（輸出時用哪個遮罩模板）
privacy_violation_flag（存在性旗標即可）
這樣做的好處：四海皆準，因為你輸出的是「policy refs + verdict」，不是法律文本。
B) Gate/Admission：加入 Privacy Validity Check（最小 1 個判斷，卻是最值錢的 moat）
在 BREL 的 admission 判定流程裡，加一個不吃 payload 的 check：
根據 profile_ref / domain_adapter_ref 判斷此 Attempt 是否屬於「可能涉及個資/可識別流」（open set）
若是，則要求 privacy_policy_ref + disclosure_scope_ref + retention_ref 的存在且有效（versioned / not stale）
不滿足 → verdict 直接 DEGRADE / DENY（由 policy 決定）
同時把結果寫回 Proof Card：
privacy_check_verdict: PASS/FAIL/INCONCLUSIVE
missing_evidence_class: PRIVACY_POLICY_MISSING / SCOPE_UNBOUND / RETENTION_UNKNOWN …
注意：你不是在做內容檢測（DLP），你是在做 承認條件（recognition constitution）。這點非常關鍵、也最能避免被說成 prior art。
C) Egress：新增 Minimal-Disclosure Egress Gate（出口治理）
BREL 很容易被誤解成「你們在收集資料」。要把這個疑慮一次打穿：加一個出口閘，所有對外輸出都要過它。
Minimal-Disclosure Egress Gate 做三件事
預設只允許 PC-Min 外送
PC-Priv 外送必須具備：
disclosure_scope_ref（定義能出哪些欄位/粒度）
authority_scope_ref / delegation_ref（誰批准外送）
產生 egress_receipt_ref（attempt-bound）寫回 Proof Card
什麼被送出（在 scope_ref 裡描述）
送給誰（recipient class）
什麼原因（reason_code）
什麼窗口（window_ref）
這個 Egress Gate 一樣是四海皆準：因為每個產業都怕「資料外流/過度揭露」，只是不一定叫 GDPR。
D) BYUSE：當被拿去“結案/賠付/監管/客服”才要求升級（partial reliance admissibility 的落地）
BREL 程式新增一個簡單的 “reliance_context_ref”（或 BYUSE flag）入口：
平時沒有 BYUSE：PC-Min 足夠 → delivery-grade
一旦 BYUSE（例如 CSR/settlement/compliance 介面呼叫）：
觸發 required hooks：可能要 window_policy_id、policy_snapshot_ref、authority_scope_ref、privacy refs…
若缺 → 回傳 not-closure-grade / void-for-reliance + upgrade_requirements_ref
禁止事後用 dashboard/RCA 文字補齊升級
這樣 Rakuten 的用法就會非常順：
日常營運：低摩擦、低揭露
一進入爭議/監管/賠付：立刻升級要求（BYUSE 驅動）
